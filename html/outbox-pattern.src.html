Outbox: who moves the row to Kafka?

Same table, same write, three publishers

github.com/machado-vitor/outbox-compared

The problem

The bug you've already seen: the dual write

Two systems, two writes, no transaction covering both
Reversing the writes only moves the failure · a local retry queue is still a dual write · Kafka can't join your database's transaction

Let me start with a bug almost everyone has seen. The service saves the order in Postgres, the commit succeeds, and then it publishes the event to Kafka. If the process dies in between, the order is saved and the event never goes out: inventory never hears about the order.

Doing it the other way round doesn't help. If you publish while the transaction is still open and it aborts, you have sent an event for an order that doesn't exist.

This has a name: the dual write. Two systems, two writes, and no transaction covering both. A retry kept in a local queue outside the transaction is still writing to two places. And Kafka can't take part in the database's transaction.

The fix

The idea: write the event to the same database, in the same transaction

Who moves the row, and how does it know what has already gone out?

The fix is to write the event to the same database, in the same transaction as the order. That's the outbox table. If the order commits, the row exists; if it rolls back, the row goes with it. Each row has an event_id, a stable id the consumer uses to drop duplicates. And it has a published_at column, which the relay sets once the event goes out; the connectors never touch it.

Someone still has to take that row to Kafka. I'll call that someone the publisher: it can be a relay, which is the classic polling worker, or it can be a connector.

And the question of this talk is: who moves the row, and how does it know what has already gone out?

Three publishers

The publishers: one table, three readers

JDBC Source (a Kafka Connect connector: Kafka's own service for running connectors): the same polling, but driven by an id cursor, and no code to write.

POCs: same schema, same write; real Postgres, MySQL, Kafka and Kafka Connect (Testcontainers) · relay and JDBC Source on Postgres, Debezium on both

In this study, three publishers move rows from the same table to Kafka.

The first is the relay, the polling worker: a process you own that polls the table every so often for rows that haven't been published yet. It sends each one to Kafka and marks it as published.

The second is the JDBC Source, a Kafka Connect connector. Kafka Connect is Kafka's own service for running connectors: you hand it a JSON configuration, and you write no code. It does the same polling, but it keeps a cursor: the highest id it has seen.

The third is Debezium, also on Kafka Connect. It's CDC, change data capture: instead of reading the table, it reads the database's transaction log, the Postgres WAL or the MySQL binlog. All of them run against real Postgres, MySQL and Kafka in the tests.

Now let's walk, step by step, through the scenario that separates the three. Two concurrent transactions write to the same outbox, and all three publishers read from it.

Transaction A does its INSERT and gets id 1, but has not committed yet. The row exists, but nobody outside can see it.

Transaction B gets id 2 and commits right away. Notice: the database hands out the id at INSERT, not at COMMIT.

The publishers read. They all see only id 2 and publish B. The JDBC Source stores its cursor: the highest id it has seen, 2. Debezium actually streams; I just line it up with the others.

Now A commits. Id 1 shows up below the highest id the JDBC Source has already seen. That's not a corner case; it's everyday concurrency.

The publishers read again. The relay publishes A, because A's published_at is still null. Debezium publishes A, in the order the transactions committed. The JDBC Source publishes nothing. A is committed in the table, but it sits below the cursor, and no query will ever return it. Confluent's own docs say it plainly: incrementing mode always results in some data loss. The POC tests reproduce it.

The real difference isn't polling vs CDC: it's where the mark lives.

Remember the question from the start: how does the publisher know what has already gone out? Each one asks something different. The relay asks: which rows have a null published_at? It sends each one, waits for Kafka's ack, and only then marks it. A's published_at is still null, so the relay's next read finds it.

Debezium runs no query at all: this config is all there is. It reads the transaction log from a replication slot, in commit order. A's COMMIT enters the log after B's COMMIT, so Debezium's position can never skip past A.

The JDBC Source asks: which rows have an id above the cursor? The query does filter on published_at, but the connector never sets it, so in practice the cursor decides. When A commits, its id is already below the cursor, and nobody asks for it again.

So there are three places for the published mark: in the row itself; at a log position, assigned at commit; or in an id, assigned before commit. The real difference isn't polling versus CDC. It's where the mark lives.

None of them is free. The JDBC Source's price is silent loss, as we just saw. The other two:

The relay duplicates: if Kafka has the event but the row isn't marked, the next read sends it again; one of our tests recorded exactly that. The table grows, so purge it, for example by partitioning. Latency is the polling interval, one second in the POC.

Debezium on Postgres needs wal_level=logical, which only changes with a restart. The replication slot, Postgres's bookmark for Debezium, keeps the WAL until the connector confirms: a stopped connector means a filling disk. max_slot_wal_keep_size caps it, but trades a full disk for a lost slot, and the zero-loss guarantee with it.

On MySQL the binlog is on by default, but nothing pins it: an outage longer than the retention loses events, and the connector stops with an error. Default retention is thirty days on MySQL, one day on Cloud SQL, and zero hours on RDS. So after a two-day outage, only plain MySQL still has the binlog; on the others the connector's position is gone, and so are the events in that gap.

Decision

Which one? Two questions, then a default

Does the outbox have concurrent writers? It almost always does.
→
JDBC Source is out. incrementing loses events silently; timestamp + delay only mitigates it, and only if every transaction finishes within the delay. Still fine outside the outbox: read replicas, legacy systems without CDC.
Need low latency and commit order, and someone to own the slot or the binlog retention?
→
Yes: Debezium. Commit order in the topic, per aggregate (key = aggregate_id); zero application code, one more thing to operate.
Otherwise:
→
Relay. You own the code and the database needs no special setup; it's one class, and every failure shows up in a debugger; one instance keeps per-aggregate order.
Postgres or MySQL under Debezium: both deliver commit order; what changes is the incident, full disk or lost events.

So which one? Two questions, then a default.

First: does the outbox have concurrent writers? It almost always does, and then the JDBC Source is out. Incrementing mode loses events silently. Timestamp mode with a safety delay only narrows the window: it works only if every transaction finishes within that delay. It does fit outside the outbox, say on a read replica or a legacy system without CDC.

Second: do latency and commit order matter, and is someone going to own the slot or the binlog retention? Then Debezium. In the topic, commit order holds per aggregate, here per order, because the message key is the aggregate_id. Zero application code, but one more thing to operate.

Otherwise, the relay: you own the code and keep the database free of special setup. It's one class, and every failure shows up in a debugger. Finally, Postgres or MySQL under Debezium? Both deliver commit order; what changes is the incident: a full disk or lost events.

Wrap-up

Takeaway: where the mark lives decides what you lose

✓
Mark in the row (relay) or a position in the commit log (Debezium): a late commit is never skipped. Debezium can still lose events in an incident (lost slot, purged binlog), but then the connector stops with an error.
✗
External id cursor (JDBC Source incrementing, or any home-grown "last id seen"): a late commit is skipped, silently.
!
The safe two are still at-least-once: relay and Debezium can deliver twice, so dedupe by event_id.

One idea to take home: where the mark lives decides what you lose. In the row, or at a log position, a late commit is never skipped; if Debezium loses events, it's loud, the connector stops. In an id cursor, the JDBC Source or your own 'last id seen', a late commit vanishes silently. And even the safe two deliver twice, so dedupe by event_id. The outbox table

event_id is the dedupe key, aggregate_id the partition key, and a partial index keeps the relay's query cheap.

    event_id     uuid        ⟦NOT NULL UNIQUE⟧,  -- survives redelivery; the consumer's dedup key
    aggregate_id text        NOT NULL,         ⟦-- Kafka partition key⟧
    event_type   text        NOT NULL,
    payload      jsonb       NOT NULL,

CREATE INDEX IF NOT EXISTS outbox_unpublished ON outbox (id) ⟦WHERE published_at IS NULL⟧;
The same shape in every POC (MySQL: CHAR(36) instead of uuid). Debezium and the JDBC Source never write published_at.

Producer settings: why retries=0 and idempotence off

The relay owns retries: a row that was not acked stays NULL and is swept again.
outbox-relay/src/main/java/Relay.java:32-36props.put(⟦"acks", "all"⟧);                 // weaker lets a leader election drop a row already marked published
props.put(⟦"retries", "0"⟧);                // the relay owns retries: the row stays unpublished and is swept again
props.put(⟦!"enable.idempotence", "false"⟧); // idempotent producer requires retries > 0
props.put("request.timeout.ms", "2000");
props.put("delivery.timeout.ms", "3000");
The idempotent producer only dedupes retries within one producer session; a relay restart is a new session, so the duplicate happens anyway. That is why dedupe belongs in the consumer. RelayTest.java:84-101 pauses Kafka and asserts every copy carries the same event_id.

Scaling the relay without breaking order

The POC relay takes no lock and assumes one instance: two copies give duplicates, not loss.
Postgres 18 illustrative, not from the POCs-- (a) one active relay: leader via a session advisory lock
--     (not behind a transaction-mode pooler)
SELECT ⟦pg_try_advisory_lock(4242)⟧;   -- false = standby: sleep, try again

-- (b) N relays: each claims a disjoint batch
BEGIN;
SELECT id, event_id, aggregate_id, event_type, payload
FROM outbox WHERE published_at IS NULL
ORDER BY id LIMIT 100
⟦FOR UPDATE SKIP LOCKED⟧;              -- no row taken twice, ⟦!but order across relays is lost⟧
-- send all, wait for the acks, then:
UPDATE outbox SET published_at = now() WHERE id = ANY($1);
COMMIT;
(b) keeps a transaction open while the sends run, and two relays can publish two events of the same order out of order. Only a single leader (a) or sharding on hash(aggregate_id) keeps per-aggregate order; RelayTest.java:64-77 proves that order for one instance.

Consumer: dedupe by event_id (inbox)

Record the event_id and apply the effect in one transaction, then commit the Kafka offset.
Postgres 18 illustrative, not from the POCsCREATE TABLE processed_events (
    ⟦event_id     uuid        PRIMARY KEY⟧,
    processed_at timestamptz NOT NULL DEFAULT now()
);

-- per message, in the consumer's own transaction:
BEGIN;
INSERT INTO processed_events (event_id) VALUES ($1)
⟦ON CONFLICT (event_id) DO NOTHING⟧;   -- 0 rows = duplicate: ROLLBACK and skip
UPDATE stock SET reserved = reserved + 1 WHERE sku = $2;   -- the effect
COMMIT;
⟦!-- only now commit the Kafka offset⟧
A crash after COMMIT and before the offset commit redelivers the message, and ON CONFLICT drops it. If the effect is an external API call, pass event_id as its idempotency key: the database COMMIT does not cover the API.

Watching the log: slot lag and binlog retention

Alert before the disk fills (Postgres) or the binlog expires (MySQL).
Postgres 18 / MySQL 8.4 illustrative, not from the POCs-- Postgres: WAL each logical slot holds, and how close it is to invalidation
SELECT slot_name, active, wal_status, inactive_since,
       pg_size_pretty(⟦pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)⟧) AS retained_wal,
       pg_size_pretty(⟦safe_wal_size⟧) AS until_invalidated  -- NULL when max_slot_wal_keep_size = -1
FROM pg_replication_slots WHERE slot_type = 'logical';

-- MySQL 8.4: retention = the longest outage you survive
SELECT ⟦@@binlog_expire_logs_seconds⟧ / 86400 AS retention_days;
SHOW BINARY LOGS;          -- oldest file still on disk
SHOW BINARY LOG STATUS;    -- current position (SHOW MASTER STATUS is gone in 8.4)
Alert on disk use, an inactive slot, and retained WAL growing. For a quiet outbox, set heartbeat.interval.ms so the slot keeps advancing. Drop the slot when the connector is retired: SELECT pg_drop_replication_slot('outbox_slot');

Relay backlog and purge

Alert on the age of the oldest unpublished row, not on the row count; purge rows already published.
Postgres 18 illustrative, not from the POCs-- backlog (served by the partial index outbox_unpublished)
SELECT count(*) AS unpublished FROM outbox WHERE published_at IS NULL;

-- age needs a column the POC lacks
ALTER TABLE outbox ADD COLUMN created_at timestamptz NOT NULL DEFAULT now();
SELECT ⟦now() - min(created_at)⟧ AS oldest_unpublished
FROM outbox WHERE published_at IS NULL;

-- purge published rows in batches (cron / pg_cron)
DELETE FROM outbox WHERE id IN (
    SELECT id FROM outbox WHERE published_at < now() - interval '7 days'
    ⟦ORDER BY id LIMIT 10000⟧);
Index published_at if the purge scans. Partitioning on published_at has a catch: a partitioned table can only keep PRIMARY KEY (id) and UNIQUE (event_id) if they include the partition key, and a primary-key column cannot be NULL.
