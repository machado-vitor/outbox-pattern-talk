Outbox: relay vs JDBC Source vs Debezium

Same table, same write, three publishers
Vitor Machado
github.com/machado-vitor/outbox-compared
Postgres 18.6 · MySQL 8.4 · Kafka 4.3.1 · kafka-connect-jdbc 10.9.9 · Debezium 3.3.2.Final · 17 passing tests, 2026-10-13

Hi everyone, I'm Vitor. You have an outbox table, and you need to get those rows into Kafka. I tried three ways: a relay I wrote, Confluent's JDBC Source connector, and Debezium. All with real Postgres, MySQL and Kafka. I'll show you how each one works, what it costs, and when I'd use it.

Context

The outbox: the event is a row in the order's own transaction

The dual write: save the order, then publish. If the service dies in between, the event is never sent. Kafka can't join the database transaction.
The outbox: the event is a row, saved in the same transaction as the order. If the order rolls back, the row is gone too. event_id: used to drop duplicates · published_at: set by the relay after sending.
The publisher: whatever takes the row from the table to Kafka: a process you write, or a connector.
The publisher must know which rows were already sent. The three do it in different ways.

Quick recap of the problem. You save the order, then you send the event to Kafka. If the service dies between those two, the order is there but the event never goes out. And you can't put Kafka inside the database transaction. So, the outbox: the event is a row, in the same transaction as the order. If the order rolls back, the row goes away with it.

But someone still has to take that row to Kafka. I'll call that the publisher. And it has to know which rows it already sent. That's where the three differ.

Three publishers

The publishers: one table, three readers

relay / polling worker: a process you own that polls the table every so often, sends, and marks the row.
JDBC Source (a Kafka Connect connector: Kafka's own service for running connectors from a JSON config): the same polling, driven by an id cursor, no code to write.
Debezium (Kafka Connect): CDC, change data capture, reading the Postgres WAL / the MySQL binlog instead of the table.
POCs: same schema, same write; real Postgres, MySQL, Kafka and Kafka Connect (Testcontainers) · relay and JDBC Source on Postgres, Debezium on both

So, three publishers, same table.

The relay is a process you write yourself. Every second it reads the table, sends the new rows, and marks them as sent.

The JDBC Source is a Kafka Connect connector: a JSON file, no code. It also polls the table, but it keeps a cursor, the highest id it has seen.

And Debezium, also on Kafka Connect. This one is CDC: it doesn't read the table, it reads the transaction log, the WAL in Postgres or the binlog in MySQL.

Okay, here's the test that shows the difference. Two transactions writing to the outbox at the same time, three publishers reading it.

Transaction A inserts a row, gets id 1, but doesn't commit yet. The row is there, but nobody can see it.

Transaction B comes in, gets id 2, and commits right away. Notice: the id is given at INSERT, not at COMMIT.

Now the publishers read. They only see id 2, so all three publish B. The JDBC Source saves its cursor: 2.

Then A commits. Id 1 shows up, but it's lower than the cursor. And this is normal with concurrent transactions.

The publishers read again. The relay publishes A, because published_at is still null. Debezium publishes A, in commit order. And the JDBC Source? Nothing. A is in the table, below the cursor, and no query will ever ask for it. pause Confluent's own docs say it: incrementing mode always loses some data. Okay, now each one in detail.

Publisher 1 · code you own

Relay: the mark is in the row, written after the ack

Why A came out
The question is "is it published?", not "is the id above where I stopped?". A late commit is one more unpublished row.
The cost: a duplicate
Kafka has the event but the UPDATE never ran: the next sweep sends it again. RelayTest.java:85-101 pauses Kafka mid-send; the topic holds the same event_id twice.

What you get
· ~80 lines, one connection, no DB setup
· every failure shows up in a debugger
· latency = the poll interval (1 s here)
· the table grows: purge it

Let's start with the relay. About eighty lines, and this is the loop. Select rows where published_at is null.

Send each one, wait for the ack. If a send fails, nothing gets marked.

After the batch, one UPDATE sets published_at. Sleep a second, go again.

And that's why A was published. The relay asks "is this row published?", not "is the id bigger than the last one I saw?".

The cost is a duplicate. Kafka got the event, but the UPDATE didn't run, so the next loop sends it again. One test pauses Kafka during the send, and the topic gets the same event_id twice. The consumer just drops the second one.

Latency is the poll interval. The table grows, so you delete old rows. And you get one class, no special database setup, and when something breaks, you can debug it.

Why A was lost
Postgres and MySQL hand out the id at INSERT, not at COMMIT. A committed below the cursor, and nothing will ever ask for it again. No error, no log line.
"using incrementing mode to load data from such tables always results in some data loss" — Confluent, JDBC Source, Limitations
Timestamp mode?
Timestamp + incrementing with a safety delay only narrows the window: safe only if every transaction finishes within the delay, and now() is the transaction's start, not its commit.
Where it is fine
A single-writer table, a read replica, a legacy system without CDC: zero code, one JSON. Not an outbox with concurrent writers.
Nothing marks the table, so there is no safe purge by state either.

Now the JDBC Source. No code, just this JSON. Mode incrementing, and the cursor column is id.

And a query. It filters on published_at, but the connector never writes that column, so the filter does nothing.

This is the query that actually runs. The connector adds "id bigger than the cursor", and the cursor lives in Kafka Connect: after B, it's 2.

So that's why A was lost. The id was given at INSERT. A committed below the cursor, and nothing ever asks for it again. No error, no log line, nothing.

Timestamp mode with a delay only makes the window smaller. So the JDBC Source is fine for a single-writer table, or an old system without CDC. Not for an outbox with many writers.

Why A came out, in commit order
No query. The slot streams the WAL in commit order; A's COMMIT entered the log after B's, so the position (an LSN, kept in Kafka Connect) can't skip it.

Connector down, then back

Then Debezium. Also no code: this JSON replaces the relay. A replication slot, a publication with just the outbox table, and snapshot mode no_data.

Then the EventRouter transform turns each outbox INSERT into a Kafka record: key is the aggregate_id, event_id and event_type in headers, the payload as value.

MySQL: same transform, plus a server id and a schema history topic.

There's no query here. Debezium reads the log from the slot, in commit order. A's commit came after B's, so the position can't skip it. You get commit order, milliseconds of latency, zero application code. And if the connector goes down, the slot keeps the WAL, so nothing is lost.

The cost of Debezium is operations, and it depends on the database. Postgres needs wal_level logical, so a restart. The slot keeps the WAL until the connector confirms it, so a stopped connector fills the disk. With a limit, the slot gets dropped instead: you lose the gap, and the connector stops with an error.

On MySQL the binlog is on by default, but nothing holds it for Debezium. If the connector is down longer than the retention, you lose events, and the connector stops with an error. Thirty days on normal MySQL, one day on Cloud SQL, zero on RDS.

So, same guarantee, different incident: full disk, or lost events. Both times the connector stops with an error, so you know. Monitor the slot and the binlog age.

Decision

Which one? Two questions, then a default

Does the outbox have concurrent writers? It almost always does.
→
JDBC Source is out. incrementing loses events silently; timestamp + delay only mitigates it, and only if every transaction finishes within the delay. Still fine outside the outbox: read replicas, legacy systems without CDC.
Need low latency and commit order, and someone to own the slot or the binlog retention?
→
Yes: Debezium. Commit order in the topic, per aggregate (key = aggregate_id); zero application code, one more thing to operate.
Otherwise:
→
Relay. You own the code and the database needs no special setup; it's one class, and every failure shows up in a debugger; one instance keeps per-aggregate order.
Postgres or MySQL under Debezium: both deliver commit order; what changes is the incident, full disk or lost events.

So how do you choose? Two questions, then a default.

Does the outbox have many writers? Almost always yes, so the JDBC Source is out. Keep it for read replicas and old systems without CDC.

Do you need low latency and commit order, and will someone take care of the slot or the binlog? Then Debezium: zero application code, one more thing to operate.

If not, the relay. You own the code, the database needs nothing special, and you can debug everything. Postgres or MySQL: same guarantee, different incident.

Wrap-up

Takeaway: where the mark lives decides what you lose

✓
Mark in the row (relay) or a position in the commit log (Debezium): a late commit is never skipped. Debezium can still lose events in an incident (lost slot, purged binlog), but then the connector stops with an error.
✗
External id cursor (JDBC Source incrementing, or any home-grown "last id seen"): a late commit is skipped, silently.
!
The safe two are still at-least-once: relay and Debezium can deliver twice, so dedupe by event_id.

The outbox table

event_id is the dedupe key, aggregate_id the partition key, and a partial index keeps the relay's query cheap.
outbox-relay/schema.sql:10-19CREATE TABLE IF NOT EXISTS outbox (
    id           bigserial   PRIMARY KEY,
    event_id     uuid        NOT NULL UNIQUE,  -- survives redelivery; the consumer's dedup key
    aggregate_id text        NOT NULL,         -- Kafka partition key
    event_type   text        NOT NULL,
    payload      jsonb       NOT NULL,
    published_at timestamptz                   -- NULL = queued
);

CREATE INDEX IF NOT EXISTS outbox_unpublished ON outbox (id) WHERE published_at IS NULL;
The same shape in every POC (MySQL: CHAR(36) instead of uuid). Debezium and the JDBC Source never write published_at.

The relay loop: mark only after the ack

A crash between the send and the UPDATE causes a duplicate, never a loss.
outbox-relay/src/main/java/Relay.java:50-61    while (rs.next()) {

        record.headers().add("event_id", rs.getString("event_id").getBytes(StandardCharsets.UTF_8));
        record.headers().add("event_type", rs.getString("event_type").getBytes(StandardCharsets.UTF_8));

        published.add(rs.getLong("id"));

}

Key = aggregate_id, event_id travels as a header. A failure mid-batch re-sends the rows already acked on the next sweep (Relay.java:41-42); the consumer drops them. One blocking send().get() per row keeps order and caps throughput.

Producer settings: why retries=0 and idempotence off

The relay owns retries: a row that was not acked stays NULL and is swept again.
outbox-relay/src/main/java/Relay.java:32-36props.put("acks", "all");                 // weaker lets a leader election drop a row already marked published
props.put("retries", "0");                // the relay owns retries: the row stays unpublished and is swept again
props.put("enable.idempotence", "false"); // idempotent producer requires retries > 0
props.put("request.timeout.ms", "2000");
props.put("delivery.timeout.ms", "3000");
The idempotent producer only dedupes retries within one producer session; a relay restart is a new session, so the duplicate happens anyway. That is why dedupe belongs in the consumer. RelayTest.java:84-101 pauses Kafka and asserts every copy carries the same event_id.

Scaling the relay without breaking order

The POC relay takes no lock and assumes one instance: two copies give duplicates, not loss.
Postgres 18 illustrative, not from the POCs-- (a) one active relay: leader via a session advisory lock
--     (not behind a transaction-mode pooler)
SELECT pg_try_advisory_lock(4242);   -- false = standby: sleep, try again

-- (b) N relays: each claims a disjoint batch
BEGIN;
SELECT id, event_id, aggregate_id, event_type, payload
FROM outbox WHERE published_at IS NULL
ORDER BY id LIMIT 100
FOR UPDATE SKIP LOCKED;              -- no row taken twice, but order across relays is lost
-- send all, wait for the acks, then:
UPDATE outbox SET published_at = now() WHERE id = ANY($1);
COMMIT;
(b) keeps a transaction open while the sends run, and two relays can publish two events of the same order out of order. Only a single leader (a) or sharding on hash(aggregate_id) keeps per-aggregate order; RelayTest.java:64-77 proves that order for one instance.

Consumer: dedupe by event_id (inbox)

Record the event_id and apply the effect in one transaction, then commit the Kafka offset.
Postgres 18 illustrative, not from the POCsCREATE TABLE processed_events (
    event_id     uuid        PRIMARY KEY,
    processed_at timestamptz NOT NULL DEFAULT now()
);

-- per message, in the consumer's own transaction:
BEGIN;
INSERT INTO processed_events (event_id) VALUES ($1)
ON CONFLICT (event_id) DO NOTHING;   -- 0 rows = duplicate: ROLLBACK and skip
UPDATE stock SET reserved = reserved + 1 WHERE sku = $2;   -- the effect
COMMIT;
-- only now commit the Kafka offset
A crash after COMMIT and before the offset commit redelivers the message, and ON CONFLICT drops it. If the effect is an external API call, pass event_id as its idempotency key: the database COMMIT does not cover the API.

Watching the log: slot lag and binlog retention

Alert before the disk fills (Postgres) or the binlog expires (MySQL).
Postgres 18 / MySQL 8.4 illustrative, not from the POCs-- Postgres: WAL each logical slot holds, and how close it is to invalidation
SELECT slot_name, active, wal_status, inactive_since,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal,
       pg_size_pretty(safe_wal_size) AS until_invalidated  -- NULL when max_slot_wal_keep_size = -1
FROM pg_replication_slots WHERE slot_type = 'logical';

-- MySQL 8.4: retention = the longest outage you survive
SELECT @@binlog_expire_logs_seconds / 86400 AS retention_days;
SHOW BINARY LOGS;          -- oldest file still on disk
SHOW BINARY LOG STATUS;    -- current position (SHOW MASTER STATUS is gone in 8.4)
Alert on disk use, an inactive slot, and retained WAL growing. For a quiet outbox, set heartbeat.interval.ms so the slot keeps advancing. Drop the slot when the connector is retired: SELECT pg_drop_replication_slot('outbox_slot');

Relay backlog and purge

Alert on the age of the oldest unpublished row, not on the row count; purge rows already published.
Postgres 18 illustrative, not from the POCs-- backlog (served by the partial index outbox_unpublished)
SELECT count(*) AS unpublished FROM outbox WHERE published_at IS NULL;

-- age needs a column the POC lacks
ALTER TABLE outbox ADD COLUMN created_at timestamptz NOT NULL DEFAULT now();
SELECT now() - min(created_at) AS oldest_unpublished
FROM outbox WHERE published_at IS NULL;

-- purge published rows in batches (cron / pg_cron)
DELETE FROM outbox WHERE id IN (
    SELECT id FROM outbox WHERE published_at < now() - interval '7 days'
    ORDER BY id LIMIT 10000);
Index published_at if the purge scans. Partitioning on published_at has a catch: a partitioned table can only keep PRIMARY KEY (id) and UNIQUE (event_id) if they include the partition key, and a primary-key column cannot be NULL.
